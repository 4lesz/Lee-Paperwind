# Paperwind — 执行原则

> 版本：v1.0 ｜ 日期：2026-11-04
> 配套文档：[PRD](../PRD.md) · [设计规范](./设计规范.md) · [验收标准](./验收标准.md)

这份文档约定**怎么做**这个产品：谁决定什么、按什么顺序做、什么叫做完、出了问题怎么办。

---

## 1. 角色

| 角色 | 谁 | 职责 |
|------|----|------|
| 产品负责人 | 我（用户） | 定需求和优先级，确认文档，试用并决定是否发布 |
| 开发执行 | Claude | 写文档、设计、编码、测试、出验收记录；发现问题主动提出，不擅自改需求 |

## 2. 核心原则

### 原则 1：文档先行，文档即合同
- 顺序固定：**PRD → 设计规范 → 验收标准 → 开发 → 验收**。
- 四份文档确认后才进入开发；开发中以文档为准，代码和文档不一致时以文档为准，然后修正其中错的一方。
- 文档要改，先改文档、写清改了什么、经产品负责人确认，再改代码。

### 原则 2：数据安全高于一切
- 优先级：**不丢数据 > 不改坏数据 > 功能完整 > 好看 > 快**。
- 任何可能丢失修改的操作必须先确认；任何保存失败必须明确报错，不能静默。
- 保存出来的文件必须是能被其他 Markdown 工具正常打开的标准格式。有冲突时，宁可少一个功能，也不能写出私有格式。

### 原则 3：范围受控
- 严格按 P0 → P1 → P2 的顺序做。P0 没全部通过前，不开始 P1。
- 开发中冒出的新想法，记入 PRD 的「后续版本」，**不在当前版本顺手加**。
- 不需要的东西不做：不加设置项、不加框架、不加依赖，除非它解决了文档里写明的需求。

### 原则 4：没验证就不算完成
一个功能的「完成」（Definition of Done）必须同时满足：
1. 代码写完，能在真实桌面应用（不是浏览器模拟）里运行；
2. 对应的验收标准条目逐条通过，并留有证据（自测输出或截图）；
3. 视觉对照设计规范检查过；
4. 控制台无报错；
5. 涉及的文档已同步更新。

汇报时如实说明：哪些通过了、哪些没测、哪些没通过。**不把「应该能用」说成「已验证」**。

### 原则 5：小步迭代，每步可演示
- 按里程碑推进（见 §3），每个里程碑结束时交付一个能运行的版本和简短的演示说明（截图 + 做了什么 + 已知问题）。
- 单次改动尽量小，一次只解决一类问题，方便回退和定位。

### 原则 6：决策留痕
- 重要决策（技术选型、需求取舍、规范变更）记入 PRD「已确认的决策」表：决定了什么、为什么、日期。
- 默认决定（产品负责人没回复时我先采用的方案）必须明确标注「默认」，随时可推翻。

### 原则 7：遇到不确定，先问
需要产品负责人决定的情况：
- 需求有歧义或互相冲突；
- 实现成本明显超出预期（例如需要安装额外的大型工具）；
- 要改变已确认的文档内容；
- 要做不可撤销或影响电脑系统的操作（例如安装软件、修改系统设置、注册文件关联）。

不需要问、直接按规范做的：文档里已写明的、纯实现细节、明显的缺陷修复。

## 3. 里程碑

| 里程碑 | 内容 | 退出条件 |
|--------|------|----------|
| **M0 文档** | PRD、设计规范、验收标准、执行原则 | 产品负责人确认四份文档 |
| **M1 能用** | 桌面外壳 + 编辑器 + 打开/保存 + 格式工具栏 + 浮动菜单 | 文件操作（F）和编辑（E）的全部 P0 通过 |
| **M2 好用** | 大纲、源码/阅读模式、深色模式、草稿恢复、本地图片、表格 | 全部 P0 + R/M 类 P1 通过；完成第一轮视觉验收 |
| **M2.5 连续写作** | 文件夹篇目、上一篇/下一篇、文中链接跳转、阅读模式保持、记住读到哪里、编辑/阅读滑块（2026-11-04 新增，见 PRD §3.3、§3.6） | [验收标准 §8b、§8c](./验收标准.md) 全部 P0 + AC-S04 通过；N 类和 R08–R11 中 P1 不通过 ≤ 1 条；M1/M2 全部回归通过 |
| **M3 发布** | 打包安装包、文件关联、性能与稳定测试、验收记录 | 满足 [验收标准 §9](./验收标准.md) 发布门槛 |

每个里程碑结束时向产品负责人汇报，确认后进入下一个。

**中途新增需求的处理**（以 M2.5 为例）：先问清关键决定（排序依据、跳转方式、排期）→ 写入 PRD、设计规范、验收标准、执行原则 → 产品负责人确认 → 开发 → 验收记录。不在未确认前写代码。

## 4. 测试策略

| 层次 | 做法 | 覆盖 |
|------|------|------|
| 自动自测 | `scripts/selftest.cjs`：启动真实 Electron 应用，打开样本文件，模拟点击工具栏、切换模式，断言结果并截图 | 渲染、往返保真、工具栏、模式切换、控制台报错 |
| 手动测试 | 按验收标准中标为「手动」的步骤操作 | 系统对话框、拖拽、安装、文件关联、快捷键 |
| 视觉验收 | 浅色/深色截图对照设计规范 | 颜色、字号、间距、组件状态 |
| 回归 | 每次修改后重跑自测脚本；发布前全量跑一遍验收标准 | 防止改 A 坏 B |

测试样本统一放在 `samples/`，需要新场景时补充样本文件，不临时手写。

## 5. 工程约定

| 项目 | 约定 |
|------|------|
| 目录 | `electron/` 桌面主进程与预加载；`src/` 编辑器界面；`docs/` 文档；`samples/` 测试样本；`scripts/` 开发与自测脚本 |
| 样式 | 所有颜色、尺寸来自 `src/style.css` 顶部的设计变量，与设计规范 §3 一一对应 |
| 安全 | 渲染进程不开 Node 权限，只通过预加载脚本暴露最小接口；外部链接一律交给系统浏览器 |
| 依赖 | 新增依赖需说明理由；优先使用成熟、维护活跃的库 |
| 版本号 | `0.主版本.修订`，与里程碑对应：M1 = 0.1.0-alpha，M2 = 0.1.0-beta，M3 = 0.1.0 |
| 代码管理 | 建议初始化 git 仓库，每个里程碑打一个标签（需产品负责人同意后执行） |

## 6. 沟通与汇报

- 每次汇报包含：**做了什么 → 验收结果（通过/未通过/未测）→ 已知问题 → 需要你决定的事**。
- 需要决定的事一次只问一个核心问题，并给出推荐方案。
- 用中文、用产品语言描述，少用技术术语；必须用到时附一句解释。
