## 2. 应用图标（设计规范 §3.5b）

经 8 轮比较选定：暖阳橙渐变底板上的白色**线条铅笔**，上下两层抖动残影，笔尾碎成粒子向右上飞散，呼应链接跳转动效。过程：普通图形（书签 / 井号 / 叠页）→ 粒子抽象图形 →「铅笔粒子化」→ 简化 → 换配色（原金色「太土」，改渐变）→ 换笔形 → 前半抖动、后半散去 → 只有剪影 / 只有线条 → 选定「线条残影」。

- 由 `scripts/make-icon.cjs`（`npm run icon`）生成 SVG 母版、16–256 共 9 个尺寸的 PNG 和 `build/icon.ico`。
- ≤ 32px 用精简版：去掉残影（残影会把笔身内部糊满，看起来像叶子），线条加粗到 5.5。24、32px 能认出铅笔；16px 只能看出轮廓，这是尺寸本身的限制。
- 检查方法：从打包后的 exe 和安装包里取出图标，确认都是新图标。

## 4. 试用反馈：「BD工作流程.md」无法正常显示（2026-11-05，规范 v1.6）

产品负责人用安装版打开自己的工作文档（Typora / Obsidian 风格，Windows 换行）。用它的副本在程序里逐屏检查，发现两类问题，产品负责人选定两项都做：

| 问题 | 原因 | 处理 |
|------|------|------|
| 「一行一条」写的内容被并成一大段（如「负责区域 / 详细地址 / 归属渠道…」） | 标准 Markdown 把段落里的单个换行当作空格 | **单个换行显示为换行**（设计规范 §5）：只影响显示，没改的段落原文保存；改过的段落里仍写为单个换行；例外：换行两边都只有图片（GitHub 的徽章）时仍排成一行 |
| Mermaid 流程图显示成一段代码 | 程序原来不支持 | **流程图**（设计规范 §5.2）：画成图；编辑时单击图展开代码、停止输入 0.3 秒后图更新；写错时提示「流程图有误：…」；跟随深浅色；判断节点用强调色浅底、节点圆角；图比正文宽时最多缩到 80%，再宽就左右滚动（产品负责人的流程图是一长条，按正文宽度缩小后字小到看不清，因此加了这条）；安全级别 strict，图里的 HTML 只当文字；组件随程序打包、只在有流程图时载入 |

文件第一行的「9# 采集项目…」是原文就这么写的（`#` 前多了一个 `9`），所以显示为普通段落，不是程序的问题。

测试样本：`samples/笔记/流程与换行.md`（自行编写，Windows 换行，不含产品负责人的文档内容）。

## 9. 性能验收（AC-P01–P05，2026-11-06）

### 9.1 怎么测的

- 新脚本：
  - `scripts/perf.cjs`：一个模式一个独立进程——先 `app.setPath('userData', 测试目录)` 再 `require('../electron/main.cjs')`，和日常使用、安装版互不影响；结果写到 `test-output/perf/<模式>/<模式>.json`；
  - `scripts/perf-run.cjs`：逐项启动、汇总、判定，写 `test-output/perf/summary.json`，并在 `dist/` 比源码旧时提醒；
  - 命令：`npm run perf`（P01 / P02 / P04，不抢焦点）、`npm run perf:keys`（P03，真实按键）、`npm run perf:all`（加 30 分钟的 P05）。
- 测的是 `vite build` 出来的 `dist/`。2026-11-06 确认安装包里的 `app.asar` 与 `dist/` 逐字节一致（§7.5）；本次重装的 beta.3 的 `app.asar` 与 `release/win-unpacked` 也逐字节一致（SHA256 `DC07A775…B815E`）。
- 环境：Windows 11 build 26200，Electron 45.2.2（Chromium 156），Node 24.17，屏幕 165Hz。
- 1MB 样本：`test-output/perf/p02/samples/perf-1mb.md`，1,050,155 字节、429,093 字，标题 / 段落 / 列表 / 引用 / 表格 / 代码块 / 清单混合（约 700 节）；含流程图的一份是 1,050,385 字节，多两个 mermaid 块。
- 不抢焦点的项用 `showInactive` + `setBackgroundThrottling(false)`；P03 窗口置顶、发真实按键（keyDown → char → keyUp）。**P03 每键间隔 300ms**：间隔小于单键耗时的话，输入事件会在队列里堆积、动画帧被饿死，测出来的是排队时间（第一版就吃过这个亏，测出 8.8 秒）。

两处口径说明：

- **AC-P04**：验收标准写的是「任务管理器」，任务管理器默认的「内存」列就是**专用工作集**。用 `Win32_PerfFormattedData_PerfProc_Process.WorkingSetPrivate`（单位是字节）合计，单位用资源管理器核对过：WorkingSet64 333MB / PrivateMemorySize64 477MB / WorkingSetPrivate 168MB，和任务管理器显示一致。工作集合计把各进程共享的 Electron DLL 重复计入，所以偏大（339MB）。
- **AC-P05** 只要求「无崩溃、无报错」，这一条通过；内存随使用上升后基本走平（15 分钟 647MB、30 分钟 663MB），但 30 分钟内没有回落，作为观察项记录。

### 9.3 P03 的根因和修复（已改代码）

- **现象**：光标在代码块里时，每按一次键比正文多约 140ms（229ms vs 87ms）。
- **原因**：Tiptap 的 `@tiptap/extension-code-block-lowlight` 只要光标在代码块里，每次改动都会把整篇所有代码块的装饰重建一遍（全量 `getDecorations` + `DecorationSet.create`），1MB 样本里有约 700 个代码块。
- **修复**（`src/editor.js`）：自己实现代码高亮插件——按节点对象判断哪些代码块真的变了，只移除并重算这几块的装饰；代码块数量变化或一次改动涉及 8 块以上才全量重建；高亮结果按「语言 + 代码」缓存（最多 2000 条）。语言没注册（如 `mermaid`）时仍按纯文本处理，保持原行为。
- **效果**：代码块内 229ms → 112.6ms，和正文接近。
- **冒烟**：`示例.md` 的 python / js 代码块着色正常；`流程与换行.md` 三个流程图正常、控制台无错误；改代码块后撤销能恢复原文。
- **剩下的差距不是高亮**：同样 1MB 内容只由段落组成时，正文输入 12–22ms（快速连打也不排队）；加入表格 / 代码 / 清单后，浏览器对 42.9 万字文档的排版每次约 60–90ms。要再往下压，需要让屏幕外的块不参与排版（虚拟化），会影响选区、查找和编辑手感，属于单独一项工作。
- **大小对照**（同样混合结构、正文输入）：100KB 10.1ms、300KB 25.2ms、600KB 47.0ms、1MB 87.1ms。

### 9.4 结论

P01、P02、P04、P05 通过；P03 按原目标（1MB 文件 ≤ 50ms）**不通过**。

**产品负责人的手动试用与决定（2026-11-06）**：用安装版（beta.3）打开 `1MB-混合.md` 和对照的 `100KB-混合.md`（即上面测试用的样本），亲自输入后反馈「没有很慢的情况」。说明：约 87ms 刚超过 50ms 的目标、低于一般能明显察觉的约 100ms；「快速连打」那组是每秒约 12 键不停顿的极端情况；中文输入法只在选字上屏时修改文档，次数更少。

决定：**接受现状，写明实测值**。验收标准 AC-P03 改为「600KB 以内单次按键 ≤ 50ms；1MB 混合文档实测约 90ms 可接受，以产品负责人手动试用不觉得卡为准」（验收标准 v1.6.1）。AC-P03 记为通过，不再卡 v0.1。「屏幕外的块不参与排版」不做，以后真遇到大文件卡顿再评估。

### 11.4 发现并修复：改名后阅读记录、草稿没有搬过来

产品负责人装好 beta.4 并启动后，`%APPDATA%\Paperwind` 里只有空的 `drafts`，没有 `reading.json`。原因：改名分支里的搬迁代码用「新数据目录不存在」判断是不是第一次启动，但 **Electron 在运行主进程代码之前就会建好（空的）数据目录**（用一个最小程序实测：主进程第一行时目录已存在），所以搬迁永远不会执行。

修复（`electron/main.cjs` 的 `migrateUserData`）：改用标记文件 `migrated-from-markdown-app` 判断只搬一次；`reading.json`、草稿只补新目录里缺的，不覆盖；界面偏好（`Local Storage`，是一个数据库）新目录里已经有了就不搬，避免混在一起。用临时目录测了两种情况：全新目录 → 三样都搬过来并写入标记；已有草稿和界面偏好的目录 → 补上阅读记录和旧草稿、保留新的草稿和界面偏好。
